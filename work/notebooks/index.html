Abstract

Which visible search pages under-capture clicks for how well they rank, and how confidently can that be found and prioritized for review? Using FlyRank's anonymized starter dataset (30,000 pages, 32 clients), a page is defined as underperforming if its click-through rate sits below its own position tier's median CTR. A hand-written baseline rule — staleness plus a flat CTR cutoff — performs worse than random at finding these pages (ROC-AUC 0.420 against a 0.496 base rate), while a Random Forest classifier trained on pre-click content and visibility features reaches 0.800 ROC-AUC and 0.98 precision@50 on a held-out set of unseen clients. Scored against the full eligible population with a minimum-visibility floor applied, the model recommends 2,836 pages for a snippet/CTR review, flags 7,332 more to monitor, and clears the remaining 11,776 — a ranked list meant to help a content team decide where limited review time goes first.

1

Problem framing

Unit of analysis: one page (content_id), one 90-day snapshot.

Output: a probability that a page's CTR underperforms its position tier, turned into one of three actions — review_snippet_ctr, monitor, no_action.

Who acts on it: a content/SEO team with limited review capacity, deciding which pages get a title/meta-description review this cycle.

Cost of a wrong call: a false positive wastes review time on a page that's fine; a false negative leaves real lost clicks unaddressed for another cycle. Neither is severe, which is why the output is a ranked list, not a hard yes/no.

Why ML helps: position alone predicts typical CTR well, but individual pages deviate from their tier's typical CTR for reasons — content type, age, freshness, depth — that a single hand-written rule can't combine the way a model can.

2

Data safety

Data used: data/raw/content_refresh_anonymized.csv — 30,000 rows, one per page, across 32 pseudonymized clients, one trailing 90-day aggregate window (not a time series).

Deliberately excluded, and why

  • ctr and clicks_90d as model features — both define the label; including either would let the model reconstruct its own answer.
  • trend_direction / trend_pct — FlyRank's own decline label, not a raw observation.
  • provider_used / model_used — marked not-for-modeling in this repo's data dictionary.
  • content_id / client_id — used only to group the train/test split, never as features.
  • No client names, domains, URLs, or raw queries appear anywhere in this repo.

A real data-quality note found while building this: 1,205 of the 2,321 rows labeled position_tier == "top_3" actually have avg_position == 0 ("no data") — over half of the "top_3" label doesn't carry real position data. This is part of why top_3 was excluded from modeling in Section 4, not just a modeling convenience.

Baseline

The rule: a page is worth reviewing if it's visible (≥500 impressions/90d) and either stale (≥180 days since last update) or under-clicking for its position (top-20 average position, CTR < 0.50%).

4

Model / analysis

Method: classification — Logistic Regression, a depth-4 Decision Tree, and Random Forest.

Target — needs_ctr_review: 1 if a page's CTR is below its own position_tier's median CTR, restricted to page_1/striking/page_3_5 (26,360 of 30,000 rows). top_3 and deep are excluded — their median CTR is exactly 0%, so "below median" is impossible there by construction.

Features (36 after one-hot encoding): search volume, competition, cpc, word/char count, days with impressions, content age, days since update, average position, impressions, two "has data" flags, plus content type, intent, competition level, freshness tier, word-count tier, position tier.

Left out on purpose: CTR and clicks (label-derived), and post-click metrics like engagement and scroll rate — predicting a pre-click outcome from post-click behavior is causally backwards.

Leakage check: passed — no banned column reached the feature set.

5

Evaluation

Split: client-grouped — pages from the same client share templates and style, so a random row split would leak that. ~20% of clients (6 of 31) are held out entirely. With only 31 clients, one random group-split can land unbalanced by chance — 200 candidate splits were searched for the closest train/test label-rate match (seed 56: 0.496 vs. 0.496).

A follow-up check across five unrelated seeds showed train/test label-rate gaps ranging from 0.001 to 0.376 — nearly identical to wildly unbalanced, purely from which clients land in test. That range is why the search was necessary, not just cautious.

A reproducibility quirk worth naming: the Decision Tree's ROC-AUC (0.735) matched a prior run exactly, but its precision@K numbers did not. A shallow tree assigns the same probability to every sample in a leaf, so many test rows tie exactly — which tied row lands in the "top 20" depends on row order, not on anything the model learned. ROC-AUC and average precision are tie-robust; precision@K on a coarse model like this is not.

Errors: the worst false positives are tiny-volume pages where one lucky click created a spuriously high CTR; the worst false negatives are high-volume pages with a genuinely poor CTR that the model still called "fine," having learned "high volume usually means OK" as a generally-correct but imperfect rule.

6

Interpretation

impressions_90d and days_with_impressions dominate Random Forest's feature importance. This is defensible — low-volume pages produce noisy CTR ratios, so volume is a reasonable signal for how much to trust a page's own CTR — but it's also exactly why the errors above cluster at the volume extremes.

A negative result worth stating plainly: the signal audit found CTR does not track visibility volume in any consistent direction across impression tiers. The model's reliance on volume isn't rediscovering a strong direct relationship — it's using volume as a noise indicator, a different and more defensible use of the same feature.

Recommendation

Scoring all 26,360 eligible rows with the trained Random Forest and applying a ≥50-impression reliability floor (4,416 rows excluded as unreliable) leaves 21,944 actionable pages:

The top of the ranked list is consistently page_3_5/striking pages with real impression volume (50–71 impressions) and literally 0% measured CTR at decent-to-average positions — a content editor could reasonably start there tomorrow, since these are the pages most likely to have a real, fixable snippet problem rather than statistical noise.

Confidence and limits: this ranks relative underperformance within a page's own tier, not an absolute CTR standard, and covers only three of five position tiers by design.

Reproducibility

Environment: Python 3.12, pandas, scikit-learn, matplotlib.

git clone https://github.com/PrathibhaShaliniS/flyrank-internship-ml.git
cd flyrank-internship-ml
pip install pandas scikit-learn matplotlib
jupyter execute work/notebooks/capstone.ipynb --output=work/notebooks/capstone.ipynb

Random seeds: RANDOM_STATE = 42 for every model; the client-split search tried seeds 0–199 and selected 56.

Known non-determinism: Random Forest ran with n_jobs=-1; parallel execution can cause tiny floating-point differences run to run, and the Decision Tree's precision@K is sensitive to tie order (Section 5) — ROC-AUC and average precision are the numbers to trust for exact reproducibility, not precision@K on the tree.
